# Дорожная карта: AI-Native SDLC на проекте snmp2mqtt в Codex

Эталон процесса: «The AI-native SDLC playbook», Louis Claxton (Anthropic), 21.08.2026 —
https://claude.com/blog/the-ai-native-sdlc-playbook

Рабочая среда — приложение Codex. Исходный процесс для Claude Code адаптирован 2026-10-16;
роли человека, артефакты и порядок шагов сохранены. Соответствие инструментов и источники проверки:
`docs/codex-workflow.md`. Это адаптация шага 00, а не выполнение последующих шагов.

Как работаем:

- один шаг = один отдельный чат; этот файл — общий контекст для всех чатов, читается в начале каждого;
- все роли (инициатор, product owner, владелец политик, инженер, ревьюер, дежурный) исполняет один человек,
  но каждую — явно, с отдельным решением «принято / не принято»;
- после каждого шага обновляется таблица статуса в конце файла и коммитится артефакт шага;
- все изменения оформляются в отдельной ветке через PR; слияние подтверждает человек;
- шаги и статусы `accepted` утверждает человек; Codex не принимает свои артефакты;
- правила доступа из `AGENTS.md` действуют на всех шагах, включая субагентов и worktree;
- пометка ★ — шаг или элемент, которого нет в статье в явном виде; добавлен для учебного прохода одним человеком.

## 1. Сквозные принципы (по статье, с адаптацией контроля для Codex)

1. **Код больше не узкое место.** Узкие места смещаются влево (намерение, требования, дизайн)
   и вправо (ревью, релиз, эксплуатация) от фазы build.
2. **Каждый этап заканчивается коммитом артефакта.** Цепочка `intent.md → spec.md → plan.md → diff + PR →
   инцидент → intent.md` — одновременно и процесс, и аудит-трейл (автор, время, все ревизии — в git).
3. **Люди отвечают за каждое решение, требующее суждения.** Агент не может одобрить собственный код.
   Гейты стоят между этапами, а не внутри работы агента.
4. **Два слоя контроля.** Skills задают правила поведения. Детерминированные проверки выполняются
   средой, hooks и CI. Для каждого запрета проверяем, где именно он исполняется и какие пути действий
   охватывает. Один hook не заменяет изоляцию и ограничения системы деплоя.
5. **Обратная связь агенту раньше, чем человеку.** Агент сам прогоняет тесты, сборку, скриншоты
   и итерирует, пока не пройдёт. Человек видит уже проверенный результат.
6. **Метрики на каждый этап:** опережающие (время между артефактами, успех с первого прохода)
   и запаздывающие (переделки, дефекты в проде, повторные инциденты).
7. **Источник истины.** У нас нет Jira или legacy-системы: источник истины — репозиторий.
   В команде это решение принимается явно: репозиторий, legacy-система или взаимные ссылки.

## 2. Лестница внедрения (из статьи; порядок зрелости)

1. Каждый шаг промптится вручную, за один проход — **мы здесь**.
2. Автоматизация передач: слияние PR с intent.md (`status: accepted`) → генерация spec;
   принятие spec.md → планирование; merge PR → деплой после отдельного гейта релиза.
3. Параллельные сессии: один инженер ведёт несколько сессий в отдельных worktree.
4. Субагенты для повторяющихся задач (верификация, линт, упрощение).
5. Неинтерактивные запуски в CI (триаж, changelog, ответы на замечания ревью).
6. Детерминированный мониторинг → вызов агента при выходе за границы → находки возвращаются как intent.md.

## 3. Целевая структура репозитория

```
snmp2mqtt/
├── AGENTS.md                  краткий контекст и правила проекта для Codex
├── README.md
├── REVIEW.md                  шаг 05: политика ревью
├── Makefile                   шаг 03a: build / test / lint
├── go.mod                     шаг 03a
├── cmd/snmp2mqtt/             точка входа
├── internal/                  код приложения
├── intent/                    цепочка артефактов, папка на инициативу
│   ├── README.md              правила хранения и работы с инициативами
│   ├── _templates/            шаблоны intent.md / spec.md / plan.md
│   └── NNNN-YYYY-MM-DD-<slug>/ intent.md → spec.md → plan.md
├── docs/
│   ├── sdlc-roadmap.md        этот файл
│   └── codex-workflow.md      работа в Codex и соответствие инструментов
├── references/                примеры и чужие репозитории для чтения; repos/ не коммитится
├── evals/                     шаг 04: задачи-эвалы для агента
├── ops/                       шаг 06: bands.yaml, детектор, runbooks
├── .agents/
│   └── skills/<name>/SKILL.md политики Codex (шаг 02a)
├── .codex/
│   ├── config.toml            настройки проекта (шаг 03a)
│   ├── hooks.json             конфигурация hooks (шаги 03a, 04, 05)
│   ├── agents/*.toml          роли субагентов (шаг 04)
│   └── hooks/*.sh             скрипты хуков (шаги 03a, 04, 05)
└── .github/workflows/         шаги 04–06, если репозиторий на GitHub
```

Это целевая структура: файлы будущих шагов создаются по мере прохождения процесса.
Правила хранения — в `intent/README.md`: `NNNN` — сквозной номер с `0001`, дата папки фиксируется
при создании intent по Москве; spec и plan добавляются в ту же папку после принятия предыдущего артефакта.
`_templates` не является инициативой.

## 4. Шаги

Формат каждого шага: вход → выход; гейт; что делаем; что понять как CTO; метрики; стартовый промпт для нового чата.
Новый чат называйте по номеру шага (например «01 PLAN»), промпт копируйте целиком.

### 00 — Организация пространства ✅ (общий чат)

Созданы начальная структура без Go-модуля и кода, шаблоны, этот файл и git-репозиторий.
При адаптации под Codex инструкции из `CLAUDE.md` сведены в `AGENTS.md`, старый файл удалён,
пустые заготовки `.claude/` перенесены в `.agents/skills/` и `.codex/`.
Действующих навыков, hooks и настроек пока нет. Следующий шаг — 01 PLAN.
2026-10-17 закреплён формат инициатив `intent/NNNN-YYYY-MM-DD-<slug>/`; шаблоны перенесены в `intent/_templates/`.

### 01 — PLAN: намерение как intent.md

- **Вход → выход:** идея в голове → `intent/NNNN-YYYY-MM-DD-<slug>/intent.md`, `status: accepted`.
- **Гейт:** product owner принимает intent. Отклонение — тоже результат, он фиксируется.
- **Что делаем:** вы рассказываете идею своими словами; Codex задаёт уточняющие вопросы и раскладывает
  ответы по `intent/_templates/intent.md`. Вы правите текст, меняете статус, коммитите.
- **Что понять как CTO:**
  - намерение фиксирует инициатор, один раз, своими словами — исчезает очередь «ждём аналитика»;
    аналитик из писателя становится ревьюером;
  - в команде intent пишет любой, включая не-инженеров; обсуждать черновик можно в ChatGPT,
    принятая версия хранится в репозитории; PO фильтрует поток;
  - intent — не ТЗ; открытые вопросы в нём — норма, их закрывает шаг 02.
- **Метрики:** опережающая — время от идеи до коммита intent.md (недели → часы);
  запаздывающая — доля intent, принятых на шаг 02.
- **Стартовый промпт:**

```
Прочитай AGENTS.md и docs/sdlc-roadmap.md. Мы на шаге 01 PLAN.
Я расскажу идею проекта своими словами. Задавай уточняющие вопросы (не больше 3 за раз),
пока не заполнишь все разделы intent/_templates/intent.md. Не придумывай требования за меня:
чего я не сказал — записывай в «Открытые вопросы». Результат положи в intent/NNNN-YYYY-MM-DD-<slug>/intent.md
со status: draft. Подготовь изменения к PR; принятие intent и слияние подтвержу я.
```

### 02a — ★ Политики как skills

- **Вход → выход:** ваши требования «как у нас принято» → 2–3 файла `.agents/skills/<name>/SKILL.md`.
- **Гейт:** владелец политики утверждает skill; дальше изменения skill идут через ревью, как код.
- **Что делаем:** решаете, какие политики применяются уже на этапе дизайна (в статье: brand, security,
  compliance, UX; для сетевого Go-демона кандидаты — безопасность: секреты, TLS, доступы; надёжность:
  переподключения, backpressure; наблюдаемость: логи, метрики, health). Codex оформляет их как skills
  с описанием, когда skill срабатывает.
- **Что понять как CTO:**
  - политика становится версионированным кодом с владельцем; применяется в момент написания spec,
    а не обнаруживается в ревью через недели;
  - skill — advisory-контроль; критичные правила позже получают исполнимые проверки (шаги 03a, 05);
  - в масштабе организации skills раздаются через плагины; изменения подписывают владельцы политик.
- **Стартовый промпт:**

```
Прочитай AGENTS.md и docs/sdlc-roadmap.md. Мы на шаге 02a.
Помоги сформулировать 2–3 политики, которые должны применяться при написании spec.md
для этого проекта, и оформи каждую как .agents/skills/<name>/SKILL.md.
Сначала предложи список кандидатов с обоснованием, я выберу. Правила должны быть проверяемыми
(что именно считается нарушением), а не пожеланиями.
```

### 02b — DESIGN: требования и дизайн как spec.md

- **Вход → выход:** принятый intent.md + skills → `spec.md` рядом с intent.md, `status: accepted`.
- **Гейт:** product owner принимает spec; помеченные конфликты с политиками решаются с владельцем политики до принятия.
- **Что делаем:** одна сессия. Codex получает intent.md, применяет skills, пишет требования и дизайн вместе,
  помечает места, где intent конфликтует с политикой или недоопределён. Вы решаете помеченное. Коммит spec.md.
- **Что понять как CTO:**
  - требования и дизайн схлопываются в одну сессию — исчезает передача «аналитик → архитектор»;
  - security и compliance участвуют через skills, а не через встречу; их роль — владеть skills и разбирать помеченное;
  - переделка spec после начала build — измеримый сигнал плохого дизайна или плохого intent.
- **Метрики:** опережающая — время между коммитами intent.md и spec.md;
  запаздывающая — коммиты в spec.md, датированные после первого коммита plan.md (переделки).
- **Стартовый промпт:**

```
Прочитай AGENTS.md и docs/sdlc-roadmap.md. Мы на шаге 02b DESIGN.
Возьми intent/NNNN-YYYY-MM-DD-<slug>/intent.md (status: accepted) и skills из .agents/skills/.
За одну сессию напиши spec.md по шаблону intent/_templates/spec.md: требования и дизайн вместе.
Каждое место, где intent конфликтует с политикой из skills или недоопределён, пометь [ТРЕБУЕТ РЕШЕНИЯ]
и спроси меня. Не закрывай открытые вопросы intent.md своими предположениями.
```

### 03a — ★ Среда разработки: контекст, команды, ограждения

- **Вход → выход:** пустой каркас → `go.mod`, минимальный `cmd/snmp2mqtt/main.go`, `Makefile`
  (build / test / lint с ненулевым exit при ошибке), расширенный `AGENTS.md`, `.codex/config.toml`,
  `.codex/hooks.json` и `.codex/hooks/*.sh`.
- **Гейт:** вы принимаете AGENTS.md, настройки и hooks как код; срабатывание проверяется в приложении.
- **Решение перед шагом:** module path Go (например `github.com/<org>/snmp2mqtt`); менять потом дорого.
- **Что делаем:** модуль; Makefile; AGENTS.md — команды, ключевые соглашения (в статье пример:
  «деньги — только BigDecimal, никогда double»; у нас будут свои), обзор архитектуры, раздел
  «что Codex делает не так»; ограничения среды — разрешённые команды и доступы, запрет чтения `.env*`
  и `secrets/`; hooks — форматирование после правки и дополнительные проверки защищённых путей.
  Выбираем поддерживаемые настройки Codex и проверяем их действие; синтаксис permissions Claude не переносим.
  Для локальных hooks требуется доверие. Проверяем, что форматирование вызывается при используемом способе правки.
- **Что понять как CTO:**
  - в статье это часть BUILD, но в команде это разовая платформенная работа с отдельным владельцем (DevEx/платформа),
    а не работа над фичей;
  - AGENTS.md держим кратким; обновляем после повторной ошибки; устаревшие правила тратят контекст впустую;
  - безопасный внутренний цикл согласуется заранее; выход из проекта и сеть требуют отдельного разрешения;
  - ограничения организации и настройки проекта — разные уровни; настройка репозитория не отменяет
    принудительные политики среды.
- **Стартовый промпт:**

```
Прочитай AGENTS.md и docs/sdlc-roadmap.md. Мы на шаге 03a.
Настрой среду: go mod init <module path>, минимальный cmd/snmp2mqtt/main.go, Makefile с целями
build / test / lint (ненулевой exit при ошибке), расширь AGENTS.md (команды, соглашения,
архитектура, раздел «что Codex делает не так»). Подготовь .codex/config.toml и .codex/hooks.json
по поддерживаемой схеме Codex: ограничения доступа и первый hook — gofmt после правки .go-файлов.
Запреты: чтение .env* и secrets/; выход из проекта и сеть без согласования. Объясни, где каждый
запрет технически исполняется. Проверь реальные разрешённые и запрещённые действия на безопасных
фикстурах и срабатывание hook в приложении; укажи непроверенное. Если нужна проверка вне проекта
или в интернете, сначала запроси доступ на конкретный путь или адрес.
Каждую настройку объясни: зачем она и что случится без неё. Функциональный код не пиши — только каркас.
```

### 03b — BUILD: обсуждение плана → plan.md → код

- **Вход → выход:** принятый spec.md + среда → `plan.md` (принят и закоммичен до кода) → реализация в ветке.
- **Гейт:** инженер утверждает plan.md. «Nothing is implemented without an accepted plan.»
- **Что делаем:** Codex сначала получает задачу только на планирование по spec.md и интервьюирует вас
  (что неясно, какие компромиссы);
  утверждённый план записывается в plan.md (какие файлы меняются, порядок, тесты, риски, чем докажем готовность)
  и коммитится. Затем реализация. Если план делится на независимые части — параллельные сессии в отдельных
  worktree в приложении Codex; путь вне проекта требует согласования. Для повторяющихся задач —
  субагенты, при необходимости с постоянными ролями в `.codex/agents/*.toml`.
- **Что понять как CTO:**
  - роль инженера: постановка → утверждение плана → ревью результата; ручное написание кода — исключение;
  - потолок параллелизма — не число сессий, а сколько потоков один человек может добросовестно ревьюить;
  - вывод сессии атрибутируется инженеру, который её вёл — ответственность не размывается;
  - гейт задаётся принятым plan.md и правилами процесса; режим интерфейса помогает планированию,
    но сам по себе не подтверждает принятие человеком.
- **Метрики:** опережающая — доля изменений, влитых с первого прохода реализации;
  запаздывающие — циклы переделок на изменение; соответствие влитого diff закоммиченному plan.md.
- **Стартовый промпт (задача только на планирование):**

```
Прочитай AGENTS.md и docs/sdlc-roadmap.md. Мы на шаге 03b BUILD.
Работаем от intent/NNNN-YYYY-MM-DD-<slug>/spec.md (status: accepted). Проинтервьюируй меня по всему,
что в spec неоднозначно, затем составь план по intent/_templates/plan.md и сохрани его
в intent/NNNN-YYYY-MM-DD-<slug>/plan.md со status: draft. Функциональный код не пиши до моего принятия
плана и коммита plan.md со status: accepted. Подготовь изменения к PR; слияние подтвержу я.
```

### 04 — TEST: цикл обратной связи для агента

- **Вход → выход:** код из 03b → рабочий цикл «make test / make build → Codex чинит → повтор до зелёного»;
  тест, падающий до фикса; hook, запрещающий править тесты в задаче фикса; субагент-верификатор
  `.codex/agents/verifier.toml`; `evals/` с 3–5 реальными задачами и ожидаемыми результатами (в статье 20–50)
  и правило: evals прогоняются при изменении AGENTS.md, skills, hooks и при смене модели.
- **Гейт:** вы принимаете правила защиты тестов и состав evals; проверяется фактический запуск verifier.
- **Что понять как CTO:**
  - сигнал «код работает» должен приходить до человека, иначе человек проверяет весь вывод агента;
  - защита тест-файлов требует исполнимой проверки; hook дополняется проверкой diff в CI;
  - AGENTS.md, skills, hooks — это production-конфигурация агента; её регрессии ловят только evals;
    смена модели или переписывание промпта без прогона evals — необоснованный риск;
  - evals надо перенастраивать регулярно (в статье — ежемесячно), иначе они шумят или пропускают регрессии.
- **Метрики:** опережающая — успех CI с первого прохода для изменений, написанных агентом;
  запаздывающие — время ревью на PR; change failure rate из трекера инцидентов.
- **Стартовый промпт:**

```
Прочитай AGENTS.md и docs/sdlc-roadmap.md. Мы на шаге 04 TEST.
Проверь, что make test и make build дают ненулевой exit при ошибке. Добавь hook, который
блокирует правки *_test.go при явно заданном режиме фикса; подключи через .codex/hooks.json.
Проверь блокировку используемых инструментов правки и shell, а также контроль diff в CI.
Создай роль .codex/agents/verifier.toml по схеме Codex: запуск приложения и проверка поведения
по критериям приёмки из spec.md. Проверь реальный запуск роли. Заведи evals/ с 3–5 задачами
и скрипт их прогона. Субагенту явно передай границы доступа проекта и согласованные исключения.
Каждый элемент объясни через «какой сбой он предотвращает».
```

### 05 — DEPLOY: ревью с участием AI и hooks как гейты

- **Решения перед шагом:** правила ревью, branch protection и CI на выбранном ранее хостинге;
  что считаем «деплоем» учебного проекта (например, docker compose
  или systemd-юнит на локальной машине) и что — «продакшеном».
- **Вход → выход:** ветка с изменениями → `REVIEW.md` (проходы: баги, безопасность, соответствие политикам;
  уровни серьёзности; что пропускать; лимит мелких замечаний); ревью PR агентом по REVIEW.md; устранение
  замечаний агентом; финальное утверждение человеком; hook-гейт продакшена (`PreToolUse` в
  `.codex/hooks.json` + `.codex/hooks/production-gate.sh`), дополненный ограничениями CI/CD и доступа
  к продакшену; уровни автономии по средам (dev — в согласованных границах, staging / prod — за гейтом);
  пример управляемой политики Codex для регулируемой среды с проверенными ограничениями доступа.
- **Гейт:** утверждение code owner (branch protection). Агент не может утвердить свой код.
  «The agent may act up to the production gate and cannot pass it.»
- **Что понять как CTO:**
  - мощность ревью больше не планируется от человеческого output: все PR получают одинаковый набор проходов,
    находки ранжированы по серьёзности; человек смотрит на намерение и риск, а не на механику;
  - разрешение на прод — проверяемое условие (тикет, авторизация релиза); hook помогает его проверить,
    а система деплоя должна запрещать обход гейта;
  - неинтерактивные запуски в CI/CD, sandbox, короткоживущие токены, MCP-инструменты деплоя с областью
    на среду — так агент получает доступ ровно до нужного уровня.
- **Метрики:** опережающие — время до первого ревью (ожидание: минуты); доля замечаний, закрытых без ручного
  вмешательства; запаздывающая — дефекты и уязвимости, пойманные до merge, против ушедших в прод.
- **Стартовый промпт:**

```
Прочитай AGENTS.md и docs/sdlc-roadmap.md. Мы на шаге 05 DEPLOY. Репозиторий: <URL настроенного remote>;
«деплой» для нас — <...>; «прод» — <...>.
Напиши REVIEW.md (проходы, уровни серьёзности, что пропускать, лимит мелких замечаний) и проведи
ревью текущей ветки по нему. Затем добавь PreToolUse-hook «production gate», который блокирует
команды деплоя в прод без <условия>, подключи через .codex/hooks.json и проверь безопасной имитацией.
Опиши, как CI/CD и права доступа сохраняют гейт при обходе hook. Опиши уровни автономии по средам.
Покажи пример управляемой политики Codex по проверенной схеме и объясни отличие от .codex/config.toml.
Не запрашивай реальные секреты и не выполняй деплой в рамках проверки гейта.
```

### 06 — MAINTAIN: замыкание цикла

- **Решение перед шагом:** какую метрику контролируем и откуда её берём (для учебного проекта — например,
  доля падений CI, задержка обработки, число переподключений к MQTT).
- **Вход → выход:** работающее приложение → `ops/bands.yaml` (метрика, baseline, tiers: 1σ — только лог;
  2σ — диагностика инструментами только на чтение; 3σ — предложение PR или пред-одобренный runbook);
  детерминированный скрипт-детектор (среднее / стандартное отклонение, правила Western Electric);
  вызов Codex без человека (`codex exec` по расписанию или webhook с согласованными ограничениями);
  находка → новый
  `intent/NNNN-YYYY-MM-DD-<slug>/intent.md` в очередь триажа; отрепетированный rollback; каждый инцидент → eval в `evals/`.
  Дополнительные сканы безопасности и дежурного агента из исходного процесса в учебном проходе пропускаем.
- **Гейт:** человек над циклом. Tiers определяют, что агент может без человека; всё выше — через
  intent → spec → plan → PR.
- **Что понять как CTO:**
  - детекция детерминирована и дешева; агент вызывается только по срабатыванию и только в разрешённом tier;
  - находки не чинятся «на месте», а входят в тот же конвейер, что и идеи — цикл замкнут и аудируем;
  - запись инцидента и runbook — в version control; rollback репетируется до того, как понадобится агенту;
  - повторные инциденты одного класса должны падать, потому что каждый фикс добавляет eval.
- **Метрики:** опережающая — время от выхода за band до intent.md в очереди триажа;
  запаздывающие — доля находок, ставших влитыми фиксами; повторные инциденты того же класса.
- **Стартовый промпт:**

```
Прочитай AGENTS.md и docs/sdlc-roadmap.md. Мы на шаге 06 MAINTAIN. Контролируем метрику: <...>.
Создай ops/bands.yaml с baseline и тремя tiers, детерминированный скрипт-детектор и команду
неинтерактивного вызова codex exec при срабатывании с ограничениями, соответствующими tier.
Настройка расписания и внешних доступов требует отдельного согласования; в этом чате сначала
покажи и проверь локальный сценарий. Не запускай автоматизацию с более широкими правами, чем согласовано.
Смоделируй выход за 3σ и проведи полный путь: детекция → диагностика → intent.md → eval.
```

## 5. Анти-паттерны (из статьи)

- Legacy-система как единственный источник истины при работе в репозитории — трение синхронизации.
  Выбрать один авторитетный источник и ссылаться из второго.
- Слабая обратная связь — агент шипит непроверенный код. Всегда дать способ проверить себя: тесты, сборка, скриншот.
- Ненастроенные evals — шумят или пропускают регрессии. Регулярная перенастройка.
- Несогласованный внутренний цикл — повторные запросы одних и тех же разрешений. Доступы согласуются
  заранее в конкретных границах; это не отменяет запросов на новые пути, адреса и сервисы.
- Устаревший AGENTS.md — тратит контекст. Держать кратким; обновлять после повторной ошибки.
