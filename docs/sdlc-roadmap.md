# Дорожная карта: AI-Native SDLC на проекте snmp2mqtt

Эталон процесса: «The AI-native SDLC playbook», Louis Claxton (Anthropic), 21.08.2026 —
https://claude.com/blog/the-ai-native-sdlc-playbook

Как работаем:
- один шаг = один отдельный чат; этот файл — общий контекст для всех чатов, читается в начале каждого;
- все роли (инициатор, product owner, владелец политик, инженер, ревьюер, дежурный) исполняет один человек,
  но каждую — явно, с отдельным решением «принято / не принято»;
- после каждого шага обновляется таблица статуса в конце файла и коммитится артефакт шага;
- пометка ★ — шаг или элемент, которого нет в статье в явном виде; добавлен для учебного прохода одним человеком.

## 1. Сквозные принципы (из статьи)

1. **Код больше не узкое место.** Узкие места смещаются влево (намерение, требования, дизайн)
   и вправо (ревью, релиз, эксплуатация) от фазы build.
2. **Каждый этап заканчивается коммитом артефакта.** Цепочка `intent.md → spec.md → plan.md → diff + PR →
   инцидент → intent.md` — одновременно и процесс, и аудит-трейл (автор, время, все ревизии — в git).
3. **Люди отвечают за каждое решение, требующее суждения.** Агент не может одобрить собственный код.
   Гейты стоят между этапами, а не внутри работы агента.
4. **Два слоя контроля.** Skills — советующие (делают нарушения редкими). Hooks — детерминированные
   (делают нарушения практически невозможными). Политика сначала пишется как skill; то, что нельзя
   нарушать никогда, дублируется hook'ом.
5. **Обратная связь агенту раньше, чем человеку.** Агент сам прогоняет тесты, сборку, скриншоты
   и итерирует, пока не пройдёт. Человек видит уже проверенный результат.
6. **Метрики на каждый этап:** опережающие (время между артефактами, успех с первого прохода)
   и запаздывающие (переделки, дефекты в проде, повторные инциденты).
7. **Источник истины.** У нас нет Jira или legacy-системы: источник истины — репозиторий.
   В команде это решение принимается явно: репозиторий, legacy-система или взаимные ссылки.

## 2. Лестница внедрения (из статьи; порядок зрелости)

1. Каждый шаг промптится вручную, за один проход — **мы здесь**.
2. Автоматизация передач: коммит intent.md → генерация spec; принятие spec.md → plan mode; merge PR → деплой.
3. Параллельные сессии: один инженер ведёт несколько сессий в отдельных worktree.
4. Субагенты для повторяющихся задач (верификация, линт, упрощение).
5. Неинтерактивные запуски в CI (триаж, changelog, ответы на замечания ревью).
6. Детерминированный мониторинг → вызов агента при выходе за границы → находки возвращаются как intent.md.

│   └── templates/             шаблоны intent / spec / plan

├── ops/                       шаг 06: bands.yaml, детектор, runbooks

## 4. Шаги

Формат каждого шага: вход → выход; гейт; что делаем; что понять как CTO; метрики; стартовый промпт для нового чата.
Новый чат называйте по номеру шага (например «01 PLAN»), промпт копируйте целиком.

### 00 — Организация пространства ✅ (общий чат)

Создана структура выше (без Go-модуля и кода), шаблоны, этот файл, `CLAUDE.md`, `git init` без коммита.

### 01 — PLAN: намерение как intent.md

- **Вход → выход:** идея в голове → `intent/0001-<slug>/intent.md`, `status: accepted`.
- **Гейт:** product owner принимает intent. Отклонение — тоже результат, он фиксируется.
- **Что делаем:** вы рассказываете идею своими словами; Claude задаёт уточняющие вопросы и раскладывает
  ответы по `docs/templates/intent.md`. Вы правите текст, меняете статус, коммитите.
- **Что понять как CTO:**
  - намерение фиксирует инициатор, один раз, своими словами — исчезает очередь «ждём аналитика»;
    аналитик из писателя становится ревьюером;
  - в команде intent пишет любой, включая не-инженеров (claude.ai / Cowork + git-коннектор); PO фильтрует поток;
  - intent — не ТЗ; открытые вопросы в нём — норма, их закрывает шаг 02.
- **Метрики:** опережающая — время от идеи до коммита intent.md (недели → часы);
  запаздывающая — доля intent, принятых на шаг 02.
- **Стартовый промпт:**

```
Прочитай docs/sdlc-roadmap.md. Мы на шаге 01 PLAN.
Я расскажу идею проекта своими словами. Задавай уточняющие вопросы (не больше 3 за раз),
пока не заполнишь все разделы docs/templates/intent.md. Не придумывай требования за меня:
чего я не сказал — записывай в «Открытые вопросы». Результат положи в intent/0001-<slug>/intent.md
со status: draft. Коммит сделаю я.
```

### 02a — ★ Политики как skills

- **Вход → выход:** ваши требования «как у нас принято» → 2–3 файла `.claude/skills/<name>/SKILL.md`.
- **Гейт:** владелец политики утверждает skill; дальше изменения skill идут через ревью, как код.
- **Что делаем:** решаете, какие политики применяются уже на этапе дизайна (в статье: brand, security,
  compliance, UX; для сетевого Go-демона кандидаты — безопасность: секреты, TLS, доступы; надёжность:
  переподключения, backpressure; наблюдаемость: логи, метрики, health). Claude оформляет их как skills
  с описанием, когда skill срабатывает.
- **Что понять как CTO:**
  - политика становится версионированным кодом с владельцем; применяется в момент написания spec,
    а не обнаруживается в ревью через недели;
  - skill — advisory-контроль; то, что нельзя нарушать никогда, позже дублируется hook'ом (шаги 03a, 05);
  - в масштабе организации skills раздаются через плагины; изменения подписывают владельцы политик.
- **Стартовый промпт:**

```
Прочитай docs/sdlc-roadmap.md. Мы на шаге 02a.
Помоги сформулировать 2–3 политики, которые должны применяться при написании spec.md
для этого проекта, и оформи каждую как .claude/skills/<name>/SKILL.md.
Сначала предложи список кандидатов с обоснованием, я выберу. Правила должны быть проверяемыми
(что именно считается нарушением), а не пожеланиями.
```

### 02b — DESIGN: требования и дизайн как spec.md

- **Вход → выход:** принятый intent.md + skills → `spec.md` рядом с intent.md, `status: accepted`.
- **Гейт:** product owner принимает spec; помеченные конфликты с политиками решаются с владельцем политики до принятия.
- **Что делаем:** одна сессия. Claude получает intent.md, применяет skills, пишет требования и дизайн вместе,
  помечает места, где intent конфликтует с политикой или недоопределён. Вы решаете помеченное. Коммит spec.md.
- **Что понять как CTO:**
  - требования и дизайн схлопываются в одну сессию — исчезает передача «аналитик → архитектор»;
  - security и compliance участвуют через skills, а не через встречу; их роль — владеть skills и разбирать помеченное;
  - переделка spec после начала build — измеримый сигнал плохого дизайна или плохого intent.
- **Метрики:** опережающая — время между коммитами intent.md и spec.md;
  запаздывающая — коммиты в spec.md, датированные после первого коммита plan.md (переделки).
- **Стартовый промпт:**

```
Прочитай docs/sdlc-roadmap.md. Мы на шаге 02b DESIGN.
Возьми intent/0001-<slug>/intent.md (status: accepted) и skills из .claude/skills/.
За одну сессию напиши spec.md по шаблону docs/templates/spec.md: требования и дизайн вместе.
Каждое место, где intent конфликтует с политикой из skills или недоопределён, пометь [ТРЕБУЕТ РЕШЕНИЯ]
и спроси меня. Не закрывай открытые вопросы intent.md своими предположениями.
```

### 03a — ★ Среда разработки: контекст, команды, ограждения

- **Вход → выход:** пустой каркас → `go.mod`, минимальный `cmd/snmp2mqtt/main.go`, `Makefile`
  (build / test / lint с ненулевым exit при ошибке), расширенный `CLAUDE.md`, `.claude/settings.json`
  (permissions + первые hooks), `.claude/hooks/*.sh`.
- **Гейт:** вы принимаете CLAUDE.md и hooks как код.
- **Решение перед шагом:** module path Go (например `github.com/<org>/snmp2mqtt`); менять потом дорого.
- **Что делаем:** модуль; Makefile; CLAUDE.md — команды, ключевые соглашения (в статье пример:
  «деньги — только BigDecimal, никогда double»; у нас будут свои), обзор архитектуры, раздел
  «что Claude делает не так»; permissions — что агент делает без вопросов (git, make build/test/lint)
  и что запрещено (чтение `.env*`, `secrets/`); hooks — форматирование после правки, запрет правок защищённых путей.
- **Что понять как CTO:**
  - в статье это часть BUILD, но в команде это разовая платформенная работа с отдельным владельцем (DevEx/платформа),
    а не работа над фичей;
  - CLAUDE.md — одна страница; обновлять, когда агент ошибся дважды; устаревший CLAUDE.md тратит контекст впустую;
  - запросы разрешений во время build возвращают человека на критический путь — утверждения переносятся к гейтам
    deploy, а внутренний цикл делается безопасным и разрешённым заранее;
  - managed settings уровня организации переопределяют настройки репозитория — так политика доходит до всех команд.
- **Стартовый промпт:**

```
Прочитай docs/sdlc-roadmap.md. Мы на шаге 03a.
Настрой среду: go mod init <module path>, минимальный cmd/snmp2mqtt/main.go, Makefile с целями
build / test / lint (ненулевой exit при ошибке), расширь CLAUDE.md (команды, соглашения,
архитектура, раздел «что Claude делает не так»), создай .claude/settings.json с permissions
(allow: git, make; deny: чтение .env* и secrets/) и первым hook'ом — gofmt после правки .go-файлов.
Каждую настройку объясни: зачем она и что случится без неё. Функциональный код не пиши — только каркас.
```

### 03b — BUILD: plan mode → plan.md → код

- **Вход → выход:** принятый spec.md + среда → `plan.md` (принят и закоммичен до кода) → реализация в ветке.
- **Гейт:** инженер утверждает plan.md. «Nothing is implemented without an accepted plan.»
- **Что делаем:** Claude Code в plan mode получает spec.md и интервьюирует вас (что неясно, какие компромиссы);
  утверждённый план записывается в plan.md (какие файлы меняются, порядок, тесты, риски, чем докажем готовность)
  и коммитится. Затем реализация. Если план делится на независимые части — параллельные сессии в отдельных
  worktree (`claude --worktree <name>`); для повторяющихся задач — субагенты в `.claude/agents/`.
- **Что понять как CTO:**
  - роль инженера: постановка → утверждение плана → ревью результата; ручное написание кода — исключение;
  - потолок параллелизма — не число сессий, а сколько потоков один человек может добросовестно ревьюить;
  - вывод сессии атрибутируется инженеру, который её вёл — ответственность не размывается;
  - plan mode по умолчанию — настройка организации, а не привычка отдельных людей.
- **Метрики:** опережающая — доля изменений, влитых с первого прохода реализации;
  запаздывающие — циклы переделок на изменение; соответствие влитого diff закоммиченному plan.md.
- **Стартовый промпт (запускать в plan mode):**

```
Прочитай docs/sdlc-roadmap.md. Мы на шаге 03b BUILD.
Работаем от intent/0001-<slug>/spec.md (status: accepted). Проинтервьюируй меня по всему,
что в spec неоднозначно, затем составь план по docs/templates/plan.md и сохрани его
в intent/0001-<slug>/plan.md. Код не пиши, пока я не скажу «план принят».
```

### 04 — TEST: цикл обратной связи для агента

- **Вход → выход:** код из 03b → рабочий цикл «make test / make build → Claude чинит → повтор до зелёного»;
  тест, падающий до фикса; hook, запрещающий править тесты в задаче фикса; субагент-верификатор
  `.claude/agents/verifier.md`; `evals/` с 3–5 реальными задачами и ожидаемыми результатами (в статье 20–50)
  и правило: evals прогоняются при изменении CLAUDE.md, skills, hooks и при смене модели.
- **Гейт:** вы принимаете правила защиты тестов и состав evals.
- **Что понять как CTO:**
  - сигнал «код работает» должен приходить до человека, иначе человек проверяет весь вывод агента;
  - защита тест-файлов — случай, когда skill недостаточно и нужен hook;
  - CLAUDE.md, skills, hooks — это production-конфигурация агента; её регрессии ловят только evals;
    смена модели или переписывание промпта без прогона evals — необоснованный риск;
  - evals надо перенастраивать регулярно (в статье — ежемесячно), иначе они шумят или пропускают регрессии.
- **Метрики:** опережающая — успех CI с первого прохода для изменений, написанных агентом;
  запаздывающие — время ревью на PR; change failure rate из трекера инцидентов.
- **Стартовый промпт:**

```
Прочитай docs/sdlc-roadmap.md. Мы на шаге 04 TEST.
Проверь, что make test и make build дают ненулевой exit при ошибке. Добавь hook, который
блокирует правки *_test.go, когда задача — исправление кода (объясни, как хук отличает задачу).
Создай субагента .claude/agents/verifier.md, который запускает приложение и проверяет поведение
по критериям приёмки из spec.md. Заведи evals/ с 3–5 задачами и скрипт их прогона.
Каждый элемент объясни через «какой сбой он предотвращает».
```

### 05 — DEPLOY: ревью с участием AI и hooks как гейты

- **Решения перед шагом:** где живёт репозиторий (GitHub / GitLab / только локально) — от этого зависят
  PR-ревью, branch protection и CI; что считаем «деплоем» учебного проекта (например, docker compose
  или systemd-юнит на локальной машине) и что — «продакшеном».
- **Вход → выход:** ветка с изменениями → `REVIEW.md` (проходы: баги, безопасность, соответствие политикам;
  уровни серьёзности; что пропускать; лимит мелких замечаний); ревью PR агентом по REVIEW.md; устранение
  замечаний агентом; финальное утверждение человеком; hook-гейт продакшена (`PreToolUse` в
  `.claude/settings.json` + `.claude/hooks/production-gate.sh`); уровни автономии по средам (dev — свободно,
  staging / prod — за гейтом); пример managed settings для регулируемой среды (deny: `.env*`, `secrets/`,
  WebFetch; allow: git, make).
- **Гейт:** утверждение code owner (branch protection). Агент не может утвердить свой код.
  «The agent may act up to the production gate and cannot pass it.»
- **Что понять как CTO:**
  - мощность ревью больше не планируется от человеческого output: все PR получают одинаковый набор проходов,
    находки ранжированы по серьёзности; человек смотрит на намерение и риск, а не на механику;
  - гейты как hooks: разрешение на прод — детерминированное условие (тикет, авторизация релиза),
    а не «агент решил, что можно»;
  - неинтерактивные запуски в CI/CD, sandbox, короткоживущие токены, MCP-инструменты деплоя с областью
    на среду — так агент получает доступ ровно до нужного уровня.
- **Метрики:** опережающие — время до первого ревью (ожидание: минуты); доля замечаний, закрытых без ручного
  вмешательства; запаздывающая — дефекты и уязвимости, пойманные до merge, против ушедших в прод.
- **Стартовый промпт:**

```
Прочитай docs/sdlc-roadmap.md. Мы на шаге 05 DEPLOY. Репозиторий: <GitHub | GitLab | локально>;
«деплой» для нас — <...>; «прод» — <...>.
Напиши REVIEW.md (проходы, уровни серьёзности, что пропускать, лимит мелких замечаний) и проведи
ревью текущей ветки по нему. Затем добавь PreToolUse-hook «production gate», который блокирует
команды деплоя в прод без <условия>, и опиши уровни автономии по средам. Покажи пример managed
settings и объясни, чем они отличаются от .claude/settings.json.
```

### 06 — MAINTAIN: замыкание цикла

- **Решение перед шагом:** какую метрику контролируем и откуда её берём (для учебного проекта — например,
  доля падений CI, задержка обработки, число переподключений к MQTT).
- **Вход → выход:** работающее приложение → `ops/bands.yaml` (метрика, baseline, tiers: 1σ — только лог;
  2σ — диагностика инструментами только на чтение; 3σ — предложение PR или пред-одобренный runbook);
  детерминированный скрипт-детектор (среднее / стандартное отклонение, правила Western Electric);
  вызов Claude без человека (`claude -p` по расписанию или webhook); находка → новый
  `intent/NNNN-<slug>/intent.md` в очередь триажа; отрепетированный rollback; каждый инцидент → eval в `evals/`.
  В статье также: плановые сканы кодовой базы (Claude Security) и дежурный агент в чате (Claude Tag) —
  в учебном проходе пропускаем.
- **Гейт:** человек над циклом. Tiers определяют, что агент может без человека; всё выше — через
  intent → spec → plan → PR.
- **Что понять как CTO:**
  - детекция детерминирована и дешева; агент вызывается только по срабатыванию и только в разрешённом tier;
  - находки не чинятся «на месте», а входят в тот же конвейер, что и идеи — цикл замкнут и аудируем;
  - запись инцидента и runbook — в version control; rollback репетируется до того, как понадобится агенту;
  - повторные инциденты одного класса должны падать, потому что каждый фикс добавляет eval.
- **Метрики:** опережающая — время от выхода за band до intent.md в очереди триажа;
  запаздывающие — доля находок, ставших влитыми фиксами; повторные инциденты того же класса.
- **Стартовый промпт:**

```
Прочитай docs/sdlc-roadmap.md. Мы на шаге 06 MAINTAIN. Контролируем метрику: <...>.
Создай ops/bands.yaml с baseline и тремя tiers, детерминированный скрипт-детектор и команду
headless-вызова Claude при срабатывании с инструментами, соответствующими tier.
Смоделируй выход за 3σ и проведи полный путь: детекция → диагностика → intent.md → eval.
```

### 07 — ★ Ретроспектива и перенос на команду

- **Выход:** `docs/team-adoption.md`: роли и гейты (кто пишет intent, кто владеет skills, кто утверждает plan,
  кто code owner, кто дежурит над циклом), порядок внедрения по лестнице из раздела 2, набор метрик,
  список того, что не прижилось и почему.
- **Стартовый промпт:**

```
Прочитай docs/sdlc-roadmap.md и все артефакты в intent/, .claude/, evals/, ops/.
Составь docs/team-adoption.md: как перенести пройденный процесс на команду из <N> человек —
роли и гейты, порядок внедрения, метрики, риски. Отдельно: где один человек в шести ролях
исказил картину и что в команде будет иначе.
```

## 5. Анти-паттерны (из статьи)

- Legacy-система как единственный источник истины при работе в репозитории — трение синхронизации.
  Выбрать один авторитетный источник и ссылаться из второго.
- Слабая обратная связь — агент шипит непроверенный код. Всегда дать способ проверить себя: тесты, сборка, скриншот.
- Ненастроенные evals — шумят или пропускают регрессии. Регулярная перенастройка.
- Запросы разрешений во время build — человек снова на критическом пути. Утверждения — к гейтам deploy.
- Устаревший CLAUDE.md — тратит контекст. Одна страница; обновлять после повторной ошибки.
